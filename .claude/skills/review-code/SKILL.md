# 代码审查

对当前改动的代码进行全面审查。先读取与改动相关的项目文档，重点是 `.claude/docs/project-guidelines.md`、`.claude/docs/app-router-patterns.md` 和 `.claude/docs/data-patterns.md`。

## 审查流程

### 第一步：收集改动

运行 `git diff --stat` 和 `git diff --name-only` 获取所有改动文件列表。

### 第二步：逐项检查

对每个改动文件执行以下检查：

#### 1. 文件大小检查
- 统计每个文件的行数
- 超过 1000 行 → ⚠️ 必须给出拆分建议
- 超过 300 行 → 💡 建议考虑拆分

#### 2. 组件与客户端边界检查
检查 UI 导入是否使用当前项目已有依赖；检查带有 `'use client'` 的组件是否导入了数据库、JWT、bcrypt 或其他 Node-only 模块。

#### 3. 受保护文件检查
检查是否修改了以下文件：
- 构建配置：next.config.ts, tsconfig.json, postcss.config.mjs
- 环境变量：.env*
- 包管理：package.json, pnpm-lock.yaml, package-lock.json
- 应用入口与样式：app/layout.tsx, app/globals.css
- 请求代理：proxy.ts
- 代码规范：eslint.config.mjs

如果有修改，醒目提醒用户并说明影响。

#### 4. 页面结构检查
对于 `app/` 目录下的文件：
- 页面主文件是否只负责布局编排
- 弹窗/抽屉是否拆分为独立组件
- 数据逻辑是否拆分到 hooks
- 表格列配置是否独立文件
- 类型定义是否独立文件

#### 5. TypeScript 类型安全
- 运行 `pnpm type-check` 确保无类型错误
- 检查是否有 `any` 类型
- 确认类型导入使用 `import type`
- 验证函数参数和返回值有明确类型

#### 6. React 最佳实践
- hooks 依赖数组是否正确
- useCallback/useMemo 使用是否合理
- 是否有内存泄漏风险（事件监听器、定时器未清理）

#### 7. 数据层规范
- 是否按 `页面 -> fetch/apiClient -> app/api -> lib/mysql -> MySQL` 分层
- API 请求和响应是否有完整类型定义
- 是否使用参数化 SQL，并拒绝危险的空更新/删除条件

#### 8. 代码规范
- 命名是否符合规范（PascalCase/camelCase/UPPER_CASE）
- 是否有未使用的导入和变量
- 路径别名是否使用 @/
